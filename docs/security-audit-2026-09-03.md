# BACC OMP — Production Architecture, Security & Data Resilience Audit

**Date:** 2026-09-03 · **Scope:** `bacc-project-main` (Vite/React 19 PWA + Supabase + 5 Vercel serverless functions) · **Auditors' framing:** Vercel and Supabase are managed platforms — there is no self-hosted load balancer, app-server fleet, queue, or container orchestration in this app. SPOF/resilience analysis is framed as managed-service dependency risk, not invented on-prem infrastructure.

**Method:** Full close read of every file in `src/`, `api/`, `server/`, `supabase/migrations/`, `scripts/`, `tests/`, and root config, split across six domains (architecture/infra, database/RLS/IDOR, auth/authorization, rate limiting/abuse, secrets/logging/dependencies, OWASP/resilience/DoS). Findings are marked **CONFIRMED** (verified directly in code/SQL) or **POTENTIAL** (needs live Supabase/Vercel dashboard verification this audit could not perform from the repo alone).

**Critical scope note carried through this whole report:** `src/data/repositories/supabase/index.js` — the adapter that will translate app actions into real Supabase queries — is currently a **stub**; every method throws `"Supabase adapter is not wired"`. The app runs today entirely on an in-memory mock repository. This does **not** reduce the severity of the database findings below: the SQL migrations are real, committed, and enforced by Postgres the moment `VITE_DATA_SOURCE=supabase` is set, regardless of whether the JS client calls them yet. Because there is no custom CRUD API layer — the browser talks to Supabase directly with the public anon key — **Row-Level Security is the entire authorization boundary for this application.** Treat every RLS finding below as a pre-launch blocker, not a "fix later."

### Executive Summary

The BACC OMP codebase is architecturally sound for what it is — a browser-to-Supabase SPA with a small set of stateless PDF-export functions — but it is **not ready for production** in its current state, for one overriding reason: because there is no custom backend, **Postgres Row-Level Security is the entire authorization boundary**, and that boundary has multiple critical, code-confirmed holes. The most serious is that any signed-up user can grant themselves the `om`/`admin` role in one API call, which cascades into nearly every other access-control guarantee in the schema since most policies key off that same `profiles.role` column. Independently of that, an inspector can self-acknowledge their own compliance submission and forge another role's sign-off outright — defeating the two-person-integrity model that is this application's entire regulatory purpose. All five of the Vercel API functions are fully unauthenticated and one (the PDF export set) has an unvalidated-path filesystem read reachable by anyone with the URL. None of this has reached production yet — the Supabase adapter is still a stub — which is the good news: every finding here is fixable in the migrations and API handlers before real data or real users touch this system, and several of the hard parts (the immutability trigger, the storage path-scoping pattern, session handling, route-level auth gating) are already done correctly and just need to be applied consistently to the tables and endpoints that currently lack them.

### Architecture Assessment

The app is a Vite/React 19 PWA that talks directly to Supabase (Postgres + Auth + Storage) from the browser using the public anon key, plus five stateless Vercel functions used only for PDF generation and scheduled instance generation — there is no general-purpose backend API. This is a reasonable, low-operational-overhead architecture for a small-team, pre-production system, and the managed-service framing means classic SPOF concerns (load balancer, app-server fleet, queue) don't apply — the real dependency risk is Vercel/Supabase platform availability, which cannot be verified from code and should be documented as an explicit, accepted risk (plan tier, region, backup/PITR configuration). The two weakest points in the architecture itself are: no CI/CD of any kind, so nothing currently prevents a broken build (missing a compliance check, breaking PDF fidelity) from reaching production; and an offline-first design whose outage-detection logic checks local connectivity rather than actual backend reachability, so a genuine Supabase-side incident is handled worse than a simple loss of signal — the opposite of what the offline queue exists to protect against.

### Security Assessment

Security posture is currently weak, concentrated almost entirely in access control rather than classic injection/XSS-class bugs — no hardcoded secrets exist anywhere in the repo, no SQL injection surface exists (Supabase's client library parameterizes queries and no raw `.or()`/`.rpc()` string-building was found), and PDF generation via `pdf-lib` is not vulnerable to content-stream injection through stamped text. The real exposure is that authorization is asserted almost entirely through `profiles.role`, and that column is writable by its own owner with no guardrail, plus three tables ship with no RLS at all, plus the five API functions require no authentication whatsoever. Layered on top, there are no security response headers (no CSP, particularly relevant since the session token lives in `localStorage`), no rate limiting anywhere, and no CAPTCHA/lockout on login (mitigated only by whatever Supabase's project-level defaults happen to be, which needs dashboard confirmation). None of these individually require deep technical sophistication to exploit — most are a single crafted `fetch`/`supabase-js` call from an already-authenticated account.

### Data Security Assessment

Data-at-rest protection for the database itself is good where RLS exists and is correctly written (submission/work-order immutability is enforced by real Postgres triggers, not just app code choosing not to call update — this is the one piece of the compliance model that's genuinely bypass-proof today), and storage-object path scoping is correct for most buckets. But the gaps are serious for a system built around individually-attributable, non-repudiable sign-offs: any user can read any other user's stored signature image, self-escalate to a role that can approve/verify records, and forge sign-off rows attributed to a role they don't hold. Offline data (photos, signatures, submission content) sits unencrypted in IndexedDB on field devices for the duration between capture and sync, a reasonable but currently unmitigated tradeoff for an offline-first PWA. No hardcoded credentials or service-role keys exist anywhere in the codebase — the anon-key-only pattern is correctly followed throughout, including in the newly-audited API functions, which never touch Supabase directly at all.

### Reliability & Scalability Assessment

At current expected traffic (a small operations team, not public-internet scale) the app would likely run without issue day-to-day, but every one of its most expensive operations — PDF generation for a register/report/checklist, and instance-generation backfill — accepts unbounded, attacker-controlled input with no cap and is reachable with zero authentication, meaning availability risk here is really an access-control problem wearing a performance hat: fix the authentication gap and rate limiting, and most of the resource-exhaustion exposure closes with it. Areas that will need attention as real usage grows regardless of the security fixes: there's no pagination audit performed on list queries in this pass (flagged as a follow-up), no request timeouts anywhere so a hung call has no user-facing recovery path, no error tracking so failures are invisible until someone reports them, and the offline-sync queue has no backoff or dead-letter handling, so a single permanently-failing record retries forever with no visibility. None of these are difficult fixes; none of them have been done yet.

3. **Close the self-acknowledgment and sign-off-forgery gaps** on `checklist_submissions`/`checklist_signoffs`/`work_order_signoffs`. *Risk:* defeats the core two-person compliance guarantee. *Fix:* tighten `WITH CHECK` clauses as detailed in the findings table. *Files:* `002_rls_policies.sql`, `006_incidents_rls.sql`. *Complexity:* Low. *Breaking:* No (only removes an unintended capability).

### Existing Protections (already correctly implemented)

- **Submission/work-order immutability is enforced by real Postgres triggers** (`prevent_locked_submission_mutation`, `prevent_locked_work_order_mutation`), not just application code choosing not to call update — genuinely bypass-proof against a direct client call.
- **Photo/signature/attachment storage buckets are correctly per-user-path-scoped** (`(storage.foldername(name))[1] = auth.uid()::text`) for `checklist-photos`, `checklist-signatures`, `incident-attachments`, `work-order-signatures`, and `checklist-exports` — the one exception (`work-order-exports`) is called out above.
- **No hardcoded secrets, API keys, or credentials anywhere in the repository** — exhaustive grep across every file type found nothing; `.env` is correctly gitignored and `.env.example` contains only placeholder values.
- **Only the public anon Supabase key is used anywhere, client or server** — no service-role key exists in the codebase, and the 5 API functions never talk to Supabase at all, so there's no server-side credential to leak.
- **Route-level authentication gating is correctly implemented and race-free** — every protected route sits under a single `AppShell` guard that blocks on `loading` and redirects unauthenticated users with no flash of protected content.
- **Session lifecycle is standard-correct**: `autoRefreshToken`, `persistSession`, a properly-subscribed-and-cleaned-up `onAuthStateChange` listener, and `signOut()` that revokes the refresh token server-side rather than just clearing local state.
- **No PDF-injection vector**: `pdf-lib` encodes stamped text as PDF string operands, not raw content-stream syntax, so crafted field text cannot break out into document operators.
- **No SQL injection surface**: Supabase's client library parameterizes all queries; no raw `.or()`/`.rpc()` string-interpolation footgun was found anywhere (worth re-testing once the Supabase repository adapter is actually implemented).
- **Export filenames are sanitized** before being placed in `Content-Disposition` headers, preventing header injection.
- **No open redirects**: all navigation targets in the app are hardcoded, never derived from user-controlled query parameters.
- **Offline-sync replay is genuinely idempotent** for writes and photo uploads — records are upserted by stable client-generated ID, and photo uploads use a deterministic storage path with `upsert:true`, so a retried sync after a network hiccup overwrites rather than duplicates.
- **Daily/weekly instance-generation cadences correctly cap backfill** via `backfillDays` (the gap is limited to the other four cadences, per the findings table).
- **CORS is not permissively configured** on any of the 5 API functions (no `Access-Control-Allow-Origin` set at all) — doesn't stop direct non-browser calls (that's the missing-auth finding), but correctly prevents browser-based cross-origin abuse.
- **PWA service-worker cache correctly excludes `/api/*`**, so generated PDFs containing PII/signatures are never persisted into the offline cache.
- **`.gitignore` correctly excludes all `.env*` variants and `.vercel`.**
- **Dependency hygiene is generally good**: no hardcoded/deprecated packages of concern in the direct dependency set, dev-only tooling (Playwright, pixelmatch, pngjs) is correctly isolated from production, and the one `npm audit` finding (`fast-uri`) is confined to a build-time-only devDependency chain with no runtime reach.

## Verdict

**Production Readiness:** NOT READY

**Security Risk:** CRITICAL

**Architecture Resilience:** ADEQUATE (for a managed-platform SPA at current expected scale — the architecture choice itself is sound; the *implementation* of its security boundary is not)

**What must be fixed before this application is safe for production:** every CRITICAL finding above must be resolved before `VITE_DATA_SOURCE` is ever set to `supabase` for a real deployment — the role-escalation, missing-RLS, self-acknowledgment, sign-off-forgery, and unauthenticated-API findings are not edge cases requiring sophisticated attack techniques; each is a single crafted request from an already-legitimate (or, for the API functions, even anonymous) account. Because the Supabase adapter is still a stub and no real data has been written yet, none of this has caused harm so far — but wiring the adapter against the current, unpatched policies would ship every one of these vulnerabilities directly to production on day one. The HIGH-severity findings (CI/CD, rate limiting, monitoring, the DoS-class resource-exhaustion issues) should be closed in the same push before go-live; the MEDIUM and LOW items are reasonable to schedule shortly after launch but should not be indefinitely deferred given this system's regulatory/compliance purpose.
